# Persistent Chat, Reliable Results, and Ownership Design

## Goal

Make Advertpreneur CLI feel like a continuous product-owned conversation: a persistent transcript and composer remain visible while work runs; every task ends with a clear result card; and no worker-provider branding is emitted in user-facing responses or generated artifacts.

## Scope

This changes interactive output and generated artifact handling only. Provider selection, `/providers`, `/models`, authentication, quotas, and other technical configuration keep their current names and behavior.

## User-facing interaction

The terminal must keep three stable regions during both idle and active work:

1. A scrollable conversation transcript.
2. The existing joke/composer region, fixed directly below the transcript.
3. The existing bottom status bar, fixed at the terminal bottom.

When a task starts, Advertpreneur adds a live work card to the transcript. It has a spinner, an Advertpreneur-owned plain-language activity label, optional current action or file, and elapsed time. The card updates in place from structured activity events; it does not replace the composer, joke bar, or bottom bar.

Provider names are not used in live cards, chat messages, completion cards, or generated content. Examples are “Advertpreneur is inspecting WordPress,” “Advertpreneur is updating `theme.css`,” and “Advertpreneur needs a browser login.”

## Completion contract

Every task must close its live work card with an Advertpreneur result card. This is required for:

- successful completion;
- a tool or provider failure;
- user cancellation or interruption;
- a browser login boundary;
- an approval/deletion boundary;
- a bounded action-loop or context-limit stop.

Each card contains outcome, concise result text, actions/files when available, verification when available, and the exact next boundary where one exists. It is emitted once per task and remains in the transcript after later tasks begin.

## Ownership firewall

External workers are implementation engines, not user-facing authors. Advertpreneur provides a provider-neutral instruction contract that prohibits provider self-attribution, provider promotion, tracking links, attribution comments, and “created by” language in all chat text and artifacts.

Before rendering a worker response, Advertpreneur normalizes only explicit provider-attribution patterns to Advertpreneur wording. Before accepting a changed text artifact, it scans the newly written/modified text for explicit worker attribution patterns. If found, ADP asks the same worker to correct the artifact through the normal task loop; if the task cannot continue, ADP reports the boundary rather than silently claiming a clean result.

The scanner is deliberately narrow. It does not rewrite ordinary content merely because it discusses a provider as a legitimate subject. It targets clear attribution or promotional constructs such as “created by Antigravity,” “generated by Gemini,” “powered by Codex,” provider badges, or provider URLs placed as credits.

Advertpreneur branding is used only where an attribution is actually required by the generated content or an explicit provider credit is being replaced. It does not inject unrelated marketing copy into user files.

## Architecture

The terminal UI receives a small transcript model: immutable chat entries and one mutable active-work entry. Existing `TerminalUI` footer/composer machinery remains the input and status foundation; the renderer gains a stable transcript view above it rather than replacing it with temporary provider output.

Task orchestration owns a single finalization method. All local, Codex, and AGY paths call it with a typed result state, so result cards cannot be skipped by early returns or gateway boundaries.

A new output-ownership module owns provider-neutral instructions, response normalization, and artifact findings. Provider transports and local model paths call the same module before display/final reporting, avoiding provider-specific branding rules.

## Error handling and safety

The transcript renderer must degrade to the existing line-oriented output if Prompt Toolkit cannot create an interactive terminal surface. In fallback mode the composer/bottom-bar behavior stays intact and each live/result card is printed once as a structured line block.

Ownership normalization never edits binary files and never silently changes arbitrary source text. Its artifact guard works only on task-touched text files and reports an actionable failure if correction cannot be verified.

## Acceptance tests

- A work-state update preserves the composer, joke row, and bottom bar while changing the active transcript card.
- A success, failure, cancellation, login-needed, and approval-needed task each produce exactly one final result card.
- Chat text with provider attribution is rendered with Advertpreneur ownership and no provider credit.
- Generated HTML containing a provider credit is detected and sent back for correction; clean HTML is accepted unchanged.
- Legitimate content that merely mentions a provider in normal prose is not rewritten.
- Existing provider configuration displays remain unchanged.
